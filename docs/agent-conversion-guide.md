# Agent Conversion Guide — text plan → trip-config.json

## Назначение
Эта инструкция описывает методику конвертации текстового плана поездки (например, `docs/plan-v3-text.md`) в JSON-конфиг `src/assets/trip-config.json`.
Следуй ей **строго и пошагово** — избегай домысливания маршрута.

## 1. Принцип: текстовый план — единственный источник правды
Всё содержимое `trip-config.json` должно **полностью соответствовать** текстовому плану:
- города, даты, отели, порядок дней;
- места, активности, временные метки;
- варианты (A/B) и рекомендации.

**Запрещено:**
- менять аэропорт прибытия/вылета;
- менять порядок городов и количество ночей;
- самостоятельно переставлять дни местами;
- убирать или добавлять активности, которых нет в текстовом плане.

## 2. Порядок конвертации

### Шаг 1: Прочитать текстовый план целиком
- Пойми структуру: сколько дней, маршрут городов, особые пометки (варианты, бронирования, праздники).
- Обрати внимание на блок «Бронирование отелей» — он задаёт опорную сетку дней.

### Шаг 2: Определить границы дней и сверку
Создай таблицу соответствия: для каждой даты из текстового плана запиши:
- дата (DD-MM-YYYY);
- город/города в этот день;
- отель (startLocation/endLocation);
- список активностей с временем, типом и приоритетом;
- есть ли варианты (A/B), какой recommended.

**Сверься с таблицей отелей из плана** — количество ночей в каждом городе должно совпадать.

### Шаг 3: Заполнить поля Day
Для каждого дня заполни поля:
```json
{
  "date": "ДД-ММ-ГГГГ",
  "city": "Город или Город1 → Город2 для дней переезда",
  "startLocation": "Название отеля или предыдущей локации",
  "endLocation": "Название отеля или конечной локации",
  "schedule": [ ... ],
  "variants": [ ... ]   // только если в плане есть варианты
}
```

### Шаг 4: Заполнить schedule
Каждый пункт расписания — объект с обязательными и опциональными полями:

**Обязательные:**
- `time` — строка `"ЧЧ:ММ"` (если время не указано явно, оцени по контексту: «утром» → 08:00–09:00, «после обеда» → 14:00, «вечером» → 18:00–19:00)
- `description` — краткое описание (из текстового плана, без домысливания)
- `status` — всегда `"planned"`

**Важные (заполнять всегда, когда известно):**
- `type` — один из: `"transport"`, `"hotel"`, `"food"`, `"viewpoint"`, `"temple"`, `"museum"`, `"themepark"`, `"shopping"`
- `durationMinutes` — оценка в минутах
- `priority` — `"must"`, `"high"`, `"medium"`, `"low"` (must = нельзя пропустить, high = очень желательно)
- `estimatedCost` — в йенах (если указано в плане, если нет — 0)
- `details` — дополнительная информация из плана (нюансы маршрута, советы)

**Опциональные (если упомянуты в плане):**
- `reservationRequired` — true/false
- `weatherDependent` — true/false
- `googleMapsUrl` — ссылка на Google Maps
- `photoUrl` — ссылка на фото (только из Wikimedia Commons или других свободных источников)
- `tags` — массив строк (например: `["anime", "shopping"]`, `["nature", "photo"]`, `["wife", "knitting"]`)

### Шаг 5: Обработка вариантов (variants)
Если в плане для дня указаны варианты A и B:
- **Не дублируй** основной schedule — варианты заменяют его.
- Основной `schedule` дня может содержать **общие** для обоих вариантов активности (например, вечернюю прогулку, которая будет в любом случае), либо быть пустым/минимальным.
- Каждый вариант получает:
  ```json
  {
    "id": "a-короткий-идентификатор",
    "label": "A — читаемое название",
    "description": "Краткое описание (1 предложение)",
    "recommended": true/false,
    "schedule": [ ... ]
  }
  ```
- `recommended` — бери из плана. Если план не указывает явно, ставь `false`.

## 3. Правила заполнения полей

### 3.1. Типы активностей (type)
| Ключевое слово в плане | type |
|---|---|
| вылет, рейс, поезд, переезд, трансфер, автобус, метро, синкансэн | `"transport"` |
| заселение, отель, выселение | `"hotel"` |
| обед, ужин, завтрак, рынок (еда), кафе | `"food"` |
| храм, святилище, пагода, shrine, temple | `"temple"` |
| музей, exhibition | `"museum"` |
| парк развлечений, USJ, Universal | `"themepark"` |
| смотровая, обзорная, sky, башня, мост (вид) | `"viewpoint"` |
| магазин, шопинг, торговый, Don Quijote, Animate | `"shopping"` |
| прогулка (без конкретной достопримечательности) | `"viewpoint"` |
| замок (осмотр территории) | `"viewpoint"` |

### 3.2. Оценка durationMinutes
- Прогулка по району: 60–120 мин
- Посещение храма/замка: 60–150 мин
- Обед/ужин: 60–90 мин
- Переезд между городами: по плану (если сказано «4–5 часов» → 270)
- Музей: 120–240 мин
- USJ/тематический парк: 480–540 мин

### 3.3. Оценка estimatedCost
- Бери числа из плана, если есть.
- Если в плане нет точной суммы, ставь 0.
- Входные билеты: храмы 300–1000 йен, смотровые 1000–2500 йен, музей Гибли 1000 йен.
- **Не переводи рубли в йены самостоятельно**, если только план явно не указывает курс.

### 3.4. Теги (tags)
Рекомендуемые теги для частых тем в плане:
- Аниме/фигурки: `"anime"`, `"shopping"`, `"collectibles"`
- Природа/Фудзи: `"nature"`, `"photo"`, `"fuji"`
- Еда: `"food"`
- История/культура: `"culture"`, `"history"`, `"temple"`
- Транспорт: `"train"`, `"transfer"`, `"flight"`
- Для жены: `"wife"`, `"knitting"`, `"shopping"`
- Музыка: `"music"`, `"vinyl"`
- Вид/фото: `"viewpoint"`, `"photo"`

## 4. Бюджет, платежи и остальные секции

### 4.1. budget
Бери итоговую таблицу из плана (секция «Предварительный бюджет»).
- `totalLimit` — итоговая сумма из плана.
- `items` — каждая строка таблицы:
  ```json
  { "category": "Авиабилеты", "planned": 147000, "actual": 147000, "comment": "Уже куплены" }
  ```
- Если план указывает, что уже оплачено — заполни `actual` и `comment`.

### 4.2. payments
- Каждый подтверждённый платёж из плана (билеты, отели).
- `status`: `"paid"` или `"planned"`.

### 4.3. checklist
- Бери из секции «Что бронировать в первую очередь».
- Преобразуй каждый пункт в:
  ```json
  { "task": "текст задачи", "done": false }
  ```

### 4.4. souvenirTips
- Это **не копирование** checklist. Это советы по покупкам из плана.
- Если в плане нет отдельных советов по сувенирам, сгенерируй 3–5 советов на основе мест шопинга, упомянутых в маршруте.

### 4.5. links
- Ссылки из плана (Ghibli Museum и т.д.).
- Добавь Japan Guide, HyperDia, официальные сайты ключевых достопримечательностей.

### 4.6. shopping
- Список планируемых покупок (из плана: винил, косметика, кимоно, фигурки).
- `limit` — оцени по контексту бюджета (если план говорит «запасные 500 евро» — используй ~55000 йен).

## 5. Проверка после конвертации

Перед сохранением `trip-config.json` проверь:

- [ ] Количество объектов `days` совпадает с количеством дней в плане.
- [ ] Даты в `date` соответствуют плану (день.месяц.год).
- [ ] Города в `city` соответствуют плану — особенно дни переезда.
- [ ] Отели в `startLocation`/`endLocation` соответствуют таблице бронирования.
- [ ] Все варианты A/B корректно вынесены в `variants`.
- [ ] `reservationRequired: true` проставлено для: Ghibli, Shibuya Sky, USJ, музей Гарри Поттера, автобусы Mishima→Kawaguchiko и Kawaguchiko→Shinjuku.
- [ ] Бюджетные числа из плана перенесены без изменений.
- [ ] `appContext` содержит краткое описание поездки.
- [ ] `agentInstructions` содержит ссылку на эту инструкцию и версию текстового плана.
- [ ] JSON валиден (без trailing commas, без BOM).
- [ ] Все строки используют двойные кавычки, экранирование корректно.

## 6. Частые ошибки

1. **Подмена аэропорта.** Если план говорит «прилёт в Кансай», нельзя писать Narita.
2. **Сдвиг дат.** Если в плане переезд Осака→Киото 14 ноября, нельзя ставить 13 ноября.
3. **Пропуск остановок.** Каждое место из плана должно быть в расписании.
4. **Самодеятельность с порядком.** Текстовый план задаёт порядок — сохраняй его.
5. **Игнорирование вариантов.** Если день имеет варианты A/B, основной `schedule` не должен дублировать их содержимое.
6. **Путаница с отелями.** Используй точные названия из плана.
7. **Выдуманные цены.** Если план не указывает стоимость — ставь 0 или бери из общеизвестных данных (вход в храм ~500¥).

## 7. Формат записи agentInstructions
```json
"agentInstructions": "Источник: docs/plan-v3-text.md. Дата конвертации: ДД.ММ.ГГГГ. Следуй docs/agent-conversion-guide.md для обновлений."
```
